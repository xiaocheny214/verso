# Verso 产品说明计划书

**参赛主题：灵魂匹配局**

---

## 一、项目概述

Verso 是一款基于知乎账号与内容的社交匹配产品。它依据用户在知乎上的真实创作、关注与收藏生成能力画像，再将两位**能力恰好互补**的用户匹配在一起：一方擅长的，正是另一方本次想了解的；反过来同样成立。匹配成功后，双方在二十四小时内异步互相作答，各自教对方一块，也各自学到一块。

与市面上以相似性为条件的社交产品不同，Verso 的匹配条件是双向互补。同话题、同兴趣、同一问题下的用户不构成匹配关系。

项目名取自书页的背面。两面看上去相反，合上是同一张纸。

核心链路为：**知乎授权登录 → 生成能力画像 → 双向互补匹配 → 异步互答 → 质量评估 → 成色记录**。

---

## 二、项目背景

推荐系统的目标函数决定了它的行为：预测用户会喜欢什么，然后给他更多。这套逻辑在内容分发上是有效的，问题出在它从内容延伸到了人。今天主流社交产品的匹配条件几乎全部建立在相似性之上——同城、同好、同话题、同一标签、同一问题下的用户。

结果是用户使用越久，能接触到的人越接近他自己。

信息茧房真正的代价不在内容层面。内容的封闭尚可通过主动检索绕开；关系的封闭无法自解——当一个人身边不存在任何来自其他领域的人，他能读到的、能问到的、能被提醒到的，都来自与他相似的人。

与此同时，知乎这类平台上沉淀着大量真实的跨领域能力。一位长期撰写临床内容的医生、一位持续更新训练方法的教练、一位写了多年法律实务的从业者，他们同处一个平台，却没有任何机制让他们彼此发现并交换所长。平台把问题与答案连接得很好，把人与人连接得很少。

---

## 三、目标用户

首批目标用户需要同时满足三个条件：

1. 在某一领域已有可验证的内容产出；
2. 正在跨领域学习一件新的事；
3. 愿意投入五到十五分钟认真回答他人的一个问题。

这三条在知乎的重合度很高。持续创作专业内容、同时正在考虑转行或培养新习惯的用户，本就是该平台的主体人群。典型画像例如：从业三年的后端工程师，最近开始健身但不确定如何起步；健身教练，正在考虑转向线上业务，想了解互联网公司的产品逻辑。

明确不在目标范围内的有两类：只浏览不产出的用户，系统无法为其建立可信的能力画像；只希望获得答案而不愿回答的用户，互补结构对他们不成立。

## 四、现有方案为什么没有奏效

针对"跨领域获取他人经验"这一需求，现有方案可分为两类。

**第一类以社交形态解决，但匹配条件出了问题。** 兴趣社交与同好匹配声称帮助用户拓展社交圈，实际匹配条件仍是相似性，用户结识的人越多，所处圈层反而越稳固。随机匹配与陌生人社交保证了差异性，但双方缺乏继续交互的理由，交流通常终止于初次寒暄。

**第二类绕开社交，直接解决知识获取。** 站内提问与私信求助方向正确，但关系是单向的：提问方获得经验，回答方没有对应回报，不予回应是回答方的理性选择。付费咨询以经济激励解决了动力问题，代价是设置门槛，用户日常大量的咨询需求不足以支撑付费决策，却真实存在。通用大模型覆盖广、成本低，但输出的是领域内的平均答案，无法针对提问者的具体处境作判断，且交互在获得答案后即终止。

| 方案 | 能否跨领域 | 回答方是否有动力 | 能否形成持续关系 |
|---|---|---|---|
| 兴趣社交 / 同好匹配 | 否 | 有 | 有，但同质，无信息增量 |
| 随机匹配 / 陌生人社交 | 是 | 无 | 否 |
| 站内提问 | 是 | 弱，依赖回答者自发 | 否 |
| 私信求助 | 是 | 无 | 否 |
| 付费咨询 | 是 | 有，由付费驱动 | 通常为单次 |
| 通用大模型问答 | 是 | 不适用 | 否 |
| **Verso** | **是** | **有，双方互相需要** | **是** |

这些方案失败的原因可以归为一句：**要么提供了差异，但没有提供人；要么提供了人，但这个人没有继续投入的理由。**

我们据此得出的判断是：所需要的既不是放弃判断的随机连接，也不是把人越推越像自己的相似度计算，而是一套以**互补度**为目标的匹配机制。它依然精确，只是计算的不再是两个人有多重合，而是两个人能否恰好合上。

## 五、产品定位与核心逻辑

### 5.1 匹配条件

匹配成立要求两个方向同时覆盖：

- A 的擅长领域覆盖 B 本次想了解的问题
- B 的擅长领域覆盖 A 本次想了解的问题

仅单向覆盖不予匹配，那是答疑而非交换；双方擅长同一领域也不予匹配，不存在可交换的内容。

示例：一位从事软件开发的用户想了解如何开始力量训练，一位健身教练想了解互联网行业的工作方式，两人构成互补，匹配成立。

### 5.2 这一设计解决的是动机问题

互补条件真正改变的不是匹配精度，而是回答方的动机结构。

在所有求助模型中，回答方处于净付出的位置，因此不回应是常态。在互补结构中，回答方认真作答的原因是他同样在等待对方的答案。提问方也不再处于请求的位置——他在知乎上已有的创作构成了他的交换筹码。

这套机制因此不依赖积分、勋章或现金补贴来维持回答质量，驱动力内生于结构本身。

### 5.3 能力与需求分离

产品对每位用户维护两份完全独立的数据：

- **能力画像**：长期的、有内容证据支撑的，表示"你能提供什么"
- **本次求知请求**：一次性的、用完即结束的，表示"你这次缺什么"

用户提问过一次园艺，不会被长期标记为园艺领域。这一分离既保证了画像的可信度，也避免了长期标签被短期需求污染。

## 六、核心功能与使用流程

| 环节 | 功能 |
|---|---|
| 认证授权 | 知乎账号登录，获取用户授权的公开创作、关注与收藏 |
| 能力画像 | 从授权数据抽取能力标签，区分长期能力与近七日关注，每条标签保留来源 |
| 匹配 | 提交本次求知请求，系统执行双向互补配对 |
| 异步交流 | 配对成功后建立二十四小时关系，双方异步多轮留言 |
| 质量评估 | 用户主动表示不满意后，系统评估该次回答质量 |
| 成色 | 百分制资格分，记录评估结果并决定是否可继续进入匹配池 |

完整流程如下：

1. 用户使用知乎账号登录，系统依据其授权的创作、关注与收藏生成能力画像，每条能力标签可回溯至具体内容。
2. 用户填写一张短表单，说明本次想了解什么。该表单仅服务本次匹配。
3. 系统在候选池中寻找双向互补的对象。配对成功则双方进入同一段关系；未找到则如实展示等待状态，不降级为单向答疑或同领域配对。
4. 二十四小时内，双方各自留下对方所问内容的答案，不要求同时在线。
5. 若一方认为对方敷衍，由该用户点击不满意，系统随后评估该回答质量并据此调整成色。

## 七、与知乎社区的契合

Verso 的能力画像、匹配条件与互答场景，全部建立在知乎社区已有的内容与用户行为之上。以下四点是知乎能够支撑这一产品、并且难以被其他平台替代的原因。

### 7.1 知乎的内容本身就是能力证据

知乎沉淀的是行为证据：用户在某一领域撰写的长篇回答、长期收藏的内容、关注的创作者。这些数据由实际行为产生，每一条都可追溯到具体条目，因此可以直接作为"这个人擅长什么"的依据。

互补匹配恰好需要这样的输入。多数平台掌握的是用户自行勾选的兴趣标签，兴趣与能力之间存在实质差距，据此配对的双方往往都不具备教学能力。知乎让能力判断建立在可核查的内容之上，这是互补匹配得以成立的基础。

### 7.2 知乎的跨领域用户构成正好满足候选池要求

知乎的用户构成横跨医学、法律、理财、设计、职场、运动训练等多个领域，且每个领域都有长期创作者。

互补匹配需要在同一平台内同时找到具备某一领域能力的用户和需要该领域知识的用户，并且两人在另一个方向上也构成覆盖。这对候选池的领域广度要求很高——垂直社区的用户集中在单一方向，难以形成双向覆盖。知乎的领域分布使这种配对具备现实可能。

### 7.3 提问是知乎的原生行为

知乎用户已经习惯把困惑表述成一个具体问题。Verso 要求用户写出本次想了解的内容，这一动作与社区既有的使用习惯完全一致，用户无需额外的行为教育即可上手。

### 7.4 Verso 承接在内容之后，延长了知乎内容的价值链条

知乎在问题与答案之间建立了成熟的连接。Verso 在此基础上再进一步：用户已发布的内容证明了他的能力，这份能力可以换取一次针对他具体处境的应答。

对创作者而言，这为多年积累的专业内容提供了新的出口——此前它们主要转化为赞同数与关注数，现在可以转化为一次被明确需要的、面向具体个人的交流。对社区而言，优质内容的沉淀由此获得了新的流通方式。

### 7.5 对参赛主题的回应

"灵魂匹配局"关注从知友的兴趣、观点与内容行为出发，建立更自然的连接与关系。

Verso 的回答是：在同好之外，为知友提供一种能力互补的连接。同好在知乎已经容易找到，同一问题下即可聚集大量立场相近的用户；能力互补的对象则需要系统主动发现。同好关系是平行的，交流结束即终止；互补关系包含交换，交换构成下一次交互的理由。

## 八、核心技术与创新点

### 8.1 技术主张：确定性规则在上，模型在下

Verso 在三个环节使用语言模型：判断一条内容能否证明能力、判断一个人能否回答某个具体问题、判断一次回答是否敷衍。这三处判定直接决定用户能否被正确匹配、是否被扣分，因此系统对模型采取统一约束，可概括为一句：**确定性规则持有最终决定权，模型只提供受约束的判断输入。**

该约束在实现上落为六条：

1. **端口先于实现。** 每个使用模型的环节先定义协议接口——能力分类器、兼容性判定器、回答裁决器——领域服务只依赖接口，不依赖具体模型。
2. **每个模型实现都配有非模型对照实现。** 未配置模型时，系统分别使用规则分类器、领域层双向覆盖与"无法判断"裁决，功能完整运行，不存在因缺少模型而不可用的状态。
3. **输出结构受约束。** 模型输出经结构化模式校验：结论限定在固定枚举内，置信度限定 0 至 100，标签数量与理由长度均设上限。
4. **结构合法之后仍需语义校验。** 判定为支持时必须引用输入中确实存在的证据标识；方向标识必须恰好各出现一次。任一条不满足即视为非法输出并拒绝该次判定。
5. **异常统一收敛至保守结果。** 能力分类失败降级为规则分类；匹配校验失败判定该候选不通过；质量裁决失败判定为无法确认且不扣分。系统中不存在"模型出错导致误配或误罚"的路径。
6. **温度固定为 0。** 同一输入的判定结果稳定可复现，便于回归测试与问题定位。

这套约束的实际效果是：**模型的错误只会使匹配变少，不会使匹配变错。** 在一个以"回答者确实具备该能力"为前提的产品里，这一取舍是必要的。

以下三节分别说明三处判定的具体设计。

### 8.2 能力判定：区分兴趣与能力

互补匹配的可信度完全取决于能力判定的准确性。若系统将"收藏健身内容"识别为"具备健身能力"，配对双方均不具备向对方讲解的条件，产品随即失效。

判定的难点在于兴趣与能力在数据特征上高度相似。一位持续收藏摄影教程、关注多位摄影创作者的用户，在标签层面与专业摄影师难以区分，实际可能从未进行过拍摄实践。多数产品在此处以兴趣标签替代能力标签，回避了这一判断。

系统将每条知乎证据划分为三类信号：

| 信号 | 判定依据 | 可否构成能力 |
|---|---|---|
| 能力证明 | 用户本人创作的教程、复盘、实践总结、问题解决记录 | 可以 |
| 仅兴趣 | 收藏他人内容、关注某位创作者 | 不可以 |
| 证据不足 | 提问、表述"想学"或"不会"、仅出现领域关键词 | 不可以 |

核心设计在于将**信号分类**与**能力认定**分离，交由不同主体承担。

语言模型仅执行信号分类，为每条证据输出类别、置信度与判定理由。该证据能否晋升为可参与匹配的能力，由服务端的确定性规则裁定：来源非用户本人创作的予以排除；内容类型为提问的予以排除；信号非"能力证明"的予以排除；置信度低于 70 的予以排除。通过全部规则的证据按置信度汇总排序，每位用户最多保留三项能力，并为每项能力存储置信度最高证据的标题、链接与判定理由。

该设计的直接效果是，模型对单条证据的误判无法转化为错误的能力标签。即使模型将一条收藏记录判定为能力证明，该证据仍会在认定环节因来源不符被排除。

两个时间窗（长期能力与近七日关注）由同一批证据判定结果聚合两次得出，模型调用只发生一次。模型仅处理用户本人创作的最近二十四条内容，收藏与关注直接由规则判定为仅兴趣，既降低调用成本，也避免模型在这两类数据上产生误判。

模型不可用时系统降级至本地规则分类器。该分类器在设计上偏向漏判：文本包含"我不会""想学""求助"等表述的判定为证据不足；未包含"教程""复盘""经验""实战"等实践类表述的，同样判定为证据不足。产品接受能力标签偏少，不接受无法兑现的能力标签。

### 8.3 匹配校验：从领域匹配到问题匹配

领域标签一致，并不意味着具备回答该问题的能力。

以职场领域为例，"大一首次寻找实习"与"工作十年后跳槽"同属该领域，标签层面完全匹配，实际经验互不覆盖。同一领域内部的经验差异通常大于领域之间的差异，该现象在每一个大类中均存在，仅依赖标签配对将持续产生错误匹配。

因此系统在建立配对前增加一道语义校验：将提问方的问题原文、请求领域，以及被匹配方画像中与该领域相关的具体证据一并提交模型，判定该用户的实际经验是否支持回答这一具体问题。两个方向分别判定，均通过方可配对。

该环节同样不赋予模型最终决定权。模型输出被限制在固定结论集合内，判定为支持时必须至少引用一条输入中确实存在的证据标识；引用未知证据或输出结构不合法，一律视为非法输出并拒绝该候选。置信度低于 70 不予通过。模型调用超时或异常时跳过该候选，双方保持等待状态，不退回无证据支撑的配对。未配置模型时回退至领域层双向覆盖，系统正常运行。

校验判据中另设一条：**若该问题可由检索或通用模型直接回答，判定为不通过。** 产品不将可由 AI 解决的问题投入真人互答。真人回答的价值在于结合具体情况的判断与后续追问，而非复述通用答案。

### 8.4 质量评估：由用户触发的回答裁决

模型不参与双方交流，也不对单条消息实时评分。质量评估仅在用户主动表示不满意后触发。

触发后，系统围绕提问方本次的学习目标，评估对方留下的全部回答是否对准该目标、是否包含实质信息，并以百分制给出结果：低于 60 判定为敷衍，高于 80 判定为合格，区间内判定为无法确认。评估明确排除语气、态度与主观偏好，仅判断内容是否回应了本次问题。

仅敷衍判定影响成色。合格、无法确认以及模型调用失败，均不产生处罚。

成色为百分制资格分：满分一百，开户六十五分，敷衍一次扣五分，获得认可一次加一分，低于六十分暂停进入匹配池。该机制为资格控制而非账号封禁，分数回升即恢复匹配资格，默认配置为每位用户保留两次容错。加减分幅度与锁定线均由服务端配置。

### 8.5 匹配流程与工程实现

用户提交求知请求后，系统依次执行以下步骤：

1. **候选筛选。** 从等待池中排除本人、请求领域与本人相同者、成色不足者与已过期条件，并要求双向领域覆盖成立。
2. **候选排序。** 按双方成色分差升序排列，分差相同者先提交优先。该排序使成色相近的用户优先配对，避免长期高质量回答者被反复分配至低质量对象。
3. **语义校验。** 对前五名候选依次执行 8.3 所述的双向校验，任一方向不通过即跳过该候选。
4. **原子配对。** 并发提交场景下，多名用户可能同时选中同一候选。系统对候选条件施加行级锁（PostgreSQL 使用 `SELECT ... FOR UPDATE SKIP LOCKED`），在嵌套事务中以单条更新同时改写两条记录，并校验受影响行数须恰为 2，否则回滚并尝试下一候选。该实现保证不会出现重复配对或一人被配给两人。
5. **建立关系。** 配对成功后立即创建交流关系并写入结束时间，后续留言均挂载于该关系之下。

画像同步对数据源失败采取三档处理：三路数据源全部失败时报错并保留用户已有画像，不写入空结果；部分失败且本次抽不出任何能力时保留已有画像，不以残缺数据覆盖；部分失败但仍能抽出能力时正常写入。外部接口不稳定不会导致用户画像被清空或降级。

后端按依赖方向分为三层，领域逻辑集中于服务层。分层边界由 import-linter 的两条契约强制检查：一条约束分层依赖只能向下，一条约束接入层与任务层互不引用。该约束是可执行的检查项，而非文档约定。

登录与用户数据全部通过知乎黑客松开放平台的官方接口获取。站内身份使用仅服务端可读的会话凭证，知乎授权令牌仅保存于服务端并设置有效期，不进入响应体、日志或浏览器。

后端基于 FastAPI，业务数据存储于 PostgreSQL，会话与短期凭证存储于 Redis；前端为 Next.js 静态构建，由同域 Nginx 反向代理接口；整体通过 Docker Compose 编排部署。

## 九、后续规划与可持续性

**冷启动。** 互补条件严格，候选池较小时必然存在无法匹配的用户。这是设计的必然结果而非缺陷。解决方式不是放宽匹配条件，而是先将首批用户收敛在若干相邻领域，提高小范围内的候选密度。

**高风险领域边界。** 医学、法律、理财类问题不应仅凭一份通用能力画像进入同一套互助规则，需要单独定义安全边界与准入条件。

**可持续性。** 该机制不依赖补贴运转，回答方的动力来自对方同样在等待其答案。长期来看，用户在知乎积累的内容越多，其在 Verso 中的可交换价值越高，两者形成正向关系。
