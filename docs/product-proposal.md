# Wenju / 文局 Product Proposal

English name: **Wenju**. Chinese name: **文局**.
License: proprietary commercial (see repository `LICENSE`).
# 项目 · 产品策划案：文局（Wenju）

面向知乎垂直优质内容的轻社交匹配产品。在一篇文章上开短对局：摸鱼从内容邀人，带着问题再配问者或答主。
本期只做最小 MVP，服务可演示、可提交的一条主路径。

---

## 一、文局是什么

文局是立足于知乎优质内容的轻社交网站。它解决的问题不是「再做一个更好的推荐信息流」，而是：**让带着某个领域疑问的人，直接碰到这个领域里的人。**

关系模型只有一条：

```
用户 — 文章 — 用户
```

文章是人与人之间的桥，也是对局的「地图」。用户在一篇答主文章下看到有人，发出邀请；双方同意后进入限时房间；讨论围绕这篇文章；房间销毁；战绩留下；对话纪要可选带走。

与现有产品的根本区别在于「交付的是一局社交，而非一篇阅读」。知乎止步于阅读与关注：下滑、看完、点赞，人与人之间不发生对局。通用社交与 AI 问答则把人换成模型，或把匹配做成无内容的聊天室。文局只向游戏借**匹配仪式**（看见人、双方同意、开一局、结束），不借亲密度、头衔、头像框、账号养成。文章是地图；粘性来自匹配到对的人，而不是再做一个 QQ / 王者社交系统。

大模型不当第三个网友。匹配前静默做主题归一与排序；进房后只作为局内设施：开局话题、把讨论拉回原文、局末生成纪要。用户感知「房间和文章」，不感知「大模型产品」。

底层逻辑是「知乎内容作地图 + 站内身份与在线队列作匹配」。知乎开放平台提供授权用户的公开创作与冷启动搜索；匹配、邀请、房间、战绩、关注全部发生在文局站内，独立于知乎实时能力。

## 二、背景与战略决策

### 2.1 背景与机会

知乎沉淀了大量垂直领域的优质回答与文章。用户的真实习惯却是上班摸鱼：不断下滑推荐，或翻看关注更新，很少带着一个组织好的问题来「找人」。与此同时，想认真请教某个领域的人时，又只能在问题下留言碰运气，无法确认对方是否在线、是否愿意聊这一篇。

现有路径的空白有三块：

* **阅读不产生相遇**：信息流把人留在内容上，作者信息是展示属性，不是可邀请的对手。
* **问答不产生对局**：知乎直答与通用 LLM 直接给答案，替代了「找到这个领域的人」。
* **社交不绑内容**：陌生人匹配缺少共同地图，冷场成本高，也与知乎优质内容无关。

知乎开放平台当前能提供的，是搜索、热榜、直答，以及授权后的用户公开创作、关注与收藏。它**不能**提供「谁正在搜同一问题」「谁在线」「替你关注一个知乎账号」。因此，凡涉及在线匹配与对话的能力，本来就必须做在第三方产品里。这不是缺陷，而是产品立锥的位置：借知乎的内容与身份，做知乎不做的短对局。

黑客松场景下，作品必须可在线访问，并可接入知乎 OAuth 与开放 API。文局的主路径天然消耗这些能力：登录用 OAuth，文章池用授权用户创作 + 搜索冷启动，直答仅用于局内地图与纪要，不替代对话。

### 2.2 目标用户与核心问题

主用户有两类，都来自知乎使用习惯，但意图不同：

* **摸鱼读者**：有碎片时间，习惯下滑文章；看到同主题有人时，愿意「开一把」而不是加微信。
* **带疑问的人**：已经有一个具体问题，想碰到同问者或该领域答主，而不是先读完二十个回答。

供给侧是**已入驻并授权的答主**：他们在知乎上已有文章；授权后作品进入文局文章池。未入驻的知乎大 V 只能作为冷启动名片，不能成为可邀请、可进房的对象。

核心问题：如何以一篇知乎文章为共同地图，用接近游戏匹配的轻量仪式（看见人 → 双方同意 → 限时房间 → 战绩 / 可选纪要），让读者与问者、答主或同问者完成一次低负担相遇。

### 2.3 战略决策与边界

一句话决策：放弃「再做一个知乎信息流」和「做一个通用 AI 社交助手」，以「一篇文章上一局」为主线，先打通一条可演示链路——从看到文章、发出邀请，到双方同意进房，再到房间销毁、战绩留下、纪要可选保存。

* **决策一 · 只做人与人的短对局，不做 AI 陪聊。** 备选为首页常驻小助手、用直答替代答主。选择短对局：产品要解决的是找人，不是再包一层知乎直答。模型只做地图与纪要。
* **决策二 · 文章是地图，不是附件。** 备选为先匹配再随便聊，或匹配后进入通用聊天室。选择「房间绑定那篇文章」：共同上下文降低冷场，也使文局区别于盲盒社交。
* **决策三 · 双方同意才建房。** 备选为系统自动把两人塞进房间。选择王者式邀请：甲方邀请、乙方限时接受，拒绝或超时不建房。保护摸鱼，也保护答主。
* **决策四 · 房毁、战绩留、纪要自选。** 备选为完整私信存档。选择轻社交：实时消息默认销毁；战绩条默认生成（何时、哪篇、对手角色、是否成局）；纪要在销毁前各自勾选是否保存，保存的是纪要不是逐字稿。
* **决策五 · 站内池为主，知乎搜索为冷启动。** 备选为每次匹配都打知乎全站搜索，或只用站内用户。选择分层：可邀请的人必须来自文局注册且（答主路径上）已授权；知乎搜索只补「尚未入驻的作者名片」，不能进房。
* **决策六 · 只借游戏的匹配，不借游戏的社交养成。** 备选为效仿王者关系养成、亲密度、头衔、头像框，或效仿知乎创作中心等级与成就来做粘性。选择不做：学生作品与比赛评审看的是「知识和社交之间那条别人没做过的纽带」；把已有社交软件做过 n 次的装扮与关系链塞进来，是画蛇添足，也稀释核心创新。粘性的正确杠杆是匹配质量——配到的是自己想找的人，才会再来。

### 2.4 做与不做（团队结论）

争议焦点曾经是：匹配解决「如何找到能聊的人」之后，要不要再加一层养成 / 装扮，让没问题时也愿意打开产品。

结论已经对齐，写入边界，后续讨论不再翻案：

| 动议 | 结论 | 理由 |
|---|---|---|
| 王者式关系养成、亲密度、闺蜜、连续聊天天数 | **不做** | 有 QQ 等平替；像把王者用户的社交皮肤贴到知乎用户身上；Telegram 不为装扮买单，微信里关不掉的臃肿也不是知乎读者要的。 |
| 头衔、头像框、装扮商城 | **不做** | 不是项目特色；别人看不出能耐，只看出堆功能。 |
| 个人账号养成、成就、创作中心式等级 | **本期不做** | 知乎主页已有同类东西，搬过来不是创新；比赛时间应打磨匹配，做了反而是扣分项。 |
| 用额外社交功能提高「没问题时也来」的粘性 | **不靠这一层** | 没问题可以从摸鱼流进匹配（内容入口），而不是靠装扮把人留住。打开产品的理由仍是文章与人，不是养成。 |
| 游戏匹配机制作为知识与社交的纽带 | **做，且是唯一核心** | 这是耳目一新的部分：文章当地图、邀请开局、限时房间、战绩 / 可选纪要。 |

战绩不是亲密度。它只记录「在哪篇文章上开过一局」，服务核心玩法回顾，不演化成关系链、好友天数或装扮解锁条件。

### 2.5 本期范围（最小 MVP）

本期只做**单地图、双人、一条主路径**，保证能在有限时间内演示完整玩法：

1. 知乎 OAuth 登录（昵称、头像）。
2. 授权后同步该用户公开创作进入文章池（标题、摘要、链接、作者）。人数不足时，用知乎搜索预填演示用文章，并明确标记来源。
3. 摸鱼流：文章列表；文下展示「当前在读 / 可邀请」的在线用户（可用演示账号模拟）。
4. 邀请握手：发起 → 限时接受 / 拒绝 / 超时；仅双方同意后创建房间。
5. 限时房间：展示文章地图、开局话题（模型或规则模板）、双方文字聊天、倒计时。
6. 销毁：倒计时结束或双方离开；生成战绩条；提示是否保存纪要。
7. 战绩列表：可回顾对局卡片；若保存了纪要则可点开查看。

明确延后与不做：

* **延后**：带问题的主动匹配队列（同问者匹配、按问题找答主排队）；站内关注（仅作为「还想再碰到这个人」的弱关系，不做亲密度）；语音 / WebRTC；永久私信；推荐算法；知识库 RAG；多人对局。
* **不做（战略，不是时间不够才砍）**：亲密度 / 关系养成 / 闺蜜位；头衔、头像框、装扮；账号等级与成就体系；把王者或 QQ 的社交皮肤整体迁入。
* **不做（能力越界）**：克隆知乎首页与关注流的完整阅读产品；用直答代替进房；未授权就读取任意知乎用户完整创作；写入知乎关注 / 点赞；完整 IM。

带问题匹配与摸鱼流在产品上同属「两种入口」，但实现上摸鱼流已经能演示「从内容进匹配」。主动输入问题的队列与摸鱼邀请复用同一套房间，MVP 先做后者，前者作为下一迭代，不写进本期验收。

## 三、基本概念

### 3.1 文章池（Article Pool）

文章池是文局自己维护的内容索引，不是知乎全站镜像。

| 来源 | 如何进入 | 能否作为房间地图 | 作者能否被邀请进房 |
|---|---|---|---|
| 站内层 | 用户知乎授权后同步的公开创作；日后站内发布（延后） | 能 | 能（作者已入驻） |
| 冷启动层 | 知乎搜索缓存的标题、摘要、链接、作者展示信息 | 能（演示阅读） | 不能，只出名片 |

MVP 以站内层为匹配对象；冷启动层用于文章不够时的浏览与讲解「入驻前只能看不能邀」。

### 3.2 用户角色（在一局里的位置）

同一登录用户在不同局里可以是不同位置：

* **读者 / 问者**：从摸鱼流或问题入口进来的人。
* **答主**：这篇文章的作者，且已在文局入驻。
* **同主题读者**：也在读这篇文章或同一主题、但不是作者。

MVP 不单独做答主排队。文下可邀请的人 = 此刻也在这篇文章上的在线用户（含作者若在线）。

### 3.3 在场（Presence）

用户打开某篇文章，即对该文章（及归一后的主题）上报在场。离开页面或心跳超时则离场。在场是邀请列表的唯一来源。MVP 可用 WebSocket 或短轮询心跳。

### 3.4 邀请（Invite）

一次邀请是限时握手，绑定：发起者、被邀请者、文章 ID、倒计时。

状态：已发出 → 已接受 / 已拒绝 / 已超时 / 已取消。

只有「已接受」才创建房间。邀请不是房间。

### 3.5 房间（Room）

房间是这局的会话容器。

字段：房间 ID、文章 ID（地图）、双方用户、开始时间、结束时间、状态。

规则：

* 创建时机：双方同意之后，不是邀请发出时。
* 时限：固定时长（建议 10–15 分钟），可双方提前离开。
* 通信：房间内文字消息，经 WebSocket 转发，默认不作为永久 IM 存储。
* 销毁：到期或双方离开后关闭信道、丢弃实时消息。

### 3.6 地图与局内模型（Map）

地图 = 该房间绑定的文章（标题、摘要、原文链接、作者）。

局内模型只做三件事，且必须 grounded 在这篇文章上：

1. 开局丢出 1–3 个可讨论点（争议、结论、可追问）。
2. 讨论明显跑题时给一句拉回原文的提示（MVP 可做成手动「拉回地图」按钮 + 一次生成）。
3. 局末根据对话生成短纪要。

用户不与模型对聊。模型无独立气泡人格。额度紧时开局话题可用规则模板（从摘要截句），纪要再调用一次生成。

### 3.7 战绩（Match Record）

对局结束后默认写入一条短记录，类似王者战绩，不含聊天原文。

字段：时间、文章标题与链接、对方展示名、本局角色（读者 / 答主 / 同读）、是否成局、时长、是否保存了纪要。

用途：回顾碰过谁、从哪篇文章开的局。它不是亲密度、不是连续聊天天数、不解锁头衔或头像框。

### 3.8 纪要（Summary）

局末由模型根据地图文章 + 本局对话生成若干条结论。销毁前提示每位用户：**保存 / 不保存**，各自独立。

保存的是纪要文本，挂在该用户自己的战绩下。不保存则只留战绩条。默认不保存。

### 3.9 主题（Topic）

将文章标题、摘要或用户问题收成可匹配的主题键。MVP 可用同一 `article_id` 作为最粗的同地图匹配，不必上 embedding。主题归一留给「带问题匹配」迭代。

## 四、核心流程与原型

主界面是摸鱼流（文章列表），资产贯穿为「文章池 + 战绩」。一次完整对局如下（标注：知乎 API / 人工 / 工程 / 模型）：

1. 使用知乎账号 OAuth 登录，展示昵称与头像（知乎 / 人工）。
2. 授权后同步公开创作进入文章池；不足则用搜索预填演示文章并标记来源（知乎 / 工程）。
3. 用户在摸鱼流下滑，打开一篇文章，进入在场（人工 / 工程）。
4. 文下看到其他在场用户，发出邀请；对方弹窗倒计时接受或拒绝（人工 / 工程）。
5. 双方同意 → 创建房间，加载文章地图与开局话题（工程 / 模型）。
6. 限时文字讨论；倒计时可见（人工 / 工程）。
7. 结束：关闭房间，丢弃实时消息；写入战绩；询问是否保存纪要（工程 / 模型 / 人工）。
8. 用户在「战绩」中看到这局卡片；若保存了纪要则可回顾（人工）。

原型节奏（对应黑客松可提交 Demo）：

* 一条账号故事线即可拍完：登录 → 打开预置文章 → 第二个窗口用另一账号接受邀请 → 进房说话 → 结束看到战绩与可选纪要。
* 不要求真实大规模在线；演示用两个账号同屏即可。

## 五、核心假设与验收

### 5.1 核心假设

| # | 核心假设 | 验证方式 | 通过标准 | 失败退路 |
| - | --- | --- | --- | --- |
| 1 | 用户需要的是在优质文章上碰到人，而不是更好的推荐流或 AI 答案 | 演示全流程后访谈：是否理解「这是在这篇文章上开一局」 | ≥ 试用者能独立复述地图 / 邀请 / 销毁三件事 | 收缩为文章下在线状态 + 留言，不做房间 |
| 2 | 双方同意的邀请比自动进房更能被摸鱼用户接受 | 对比「直接拉进房」与「邀请确认」的主观打扰评价 | 多数人认为确认后进房可接受 | 改成仅答主可被邀请，读者之间不做 |
| 3 | 文章当地图能降低陌生人冷场 | 有地图开局话题 vs 空白聊天室，看前 1 分钟是否开口 | 有地图时开口率更高或开场更贴原文 | 开局改用固定问题模板，弱化模型 |
| 4 | 房毁 + 战绩 + 可选纪要足以构成回顾，而不必存全文、也不必上亲密度 | 结束后问是否觉得「这局存在过」 | 能在战绩里找回对手与文章 | 战绩外再加 24h 限时回放，仍不永久 IM |
| 7 | 比赛作品把精力放在匹配主路径上，比叠加养成更加分 | 演示与答辩只讲文章地图 + 邀请开局；功能清单不含装扮 / 等级 | 评审能复述创新点而不问「这和 QQ 有何不同」 | 继续砍非主路径，不回头加养成 |
| 5 | 授权用户的公开创作足以支撑 Demo 文章池 | 用 2 个授权账号同步 contents，能否列出可点开的文章 | 至少 1 篇可作地图完成对局 | 用知乎搜索预填 Demo 池，UI 标明冷启动 |
| 6 | 知乎 OAuth + 搜索 / 直答能说清「立足于知乎」而不越权 | 演示中明确：登录与文章来自知乎，匹配与房间是文局 | 评审能指出边界 | 文档与界面增加来源标记，避免被理解成官方功能 |

### 5.2 验收标准

统一用例：两位登录用户，在同一篇已入池文章下完成一次对局。

现状（不使用本产品）：在知乎读完文章后无法确认作者或其他读者是否愿意、是否在线聊这一篇；想找人只能留言或私信碰运气。

提议后形态（逐条可判定通过 / 不通过）：

1. **登录**：可用知乎 OAuth 登录，展示昵称、头像。
2. **文章可开局**：文章池中至少一篇有标题、摘要、原文链接、作者信息，可作为房间地图。
3. **在场可见**：打开该文章后，另一在场用户出现在可邀请列表。
4. **握手**：邀请发出后，被邀请方看到倒计时；拒绝或超时不产生房间；同意才进入房间。
5. **房间绑地图**：房内固定展示该文章；双方可发送文字消息；有明确倒计时。
6. **销毁**：结束后无法继续在该房间发消息；实时对话不作为永久私信出现。
7. **战绩**：双方战绩列表出现该局卡片（文章、对手、时长）。
8. **纪要可选**：结束时每人可选择保存或不保存纪要；保存后仅本人能在该条战绩下看到纪要。

边界与非法情况：未登录不能邀请；邀请对象已离场则失败并提示；未双方同意不建房；冷启动来源的未入驻作者不能被邀请进房；缺失地图文章时不创建房间。

## 六、与知乎开放能力的对照（给实现用）

| 产品能力 | 用哪类知乎能力 | MVP 是否必须 |
|---|---|---|
| 登录与名片 | 黑客松 OAuth | 必须 |
| 站内文章池 | `user/contents`（授权用户公开创作） | 必须（可加搜索兜底） |
| 冷启动名片 | `zhihu_search` | 可选兜底 |
| 开局话题 / 纪要 | 直答或自有 LLM；额度紧时模板 + 一次生成 | 纪要建议有，开局可模板 |
| 在场、邀请、房间、战绩 | 无对应知乎 API，全部自建 | 必须 |
| 关注、收藏作兴趣向量 | `followees` / `favorites` | 延后 |
| 问题下全部回答列表 | `question_answers`（无作者、额度低） | 不做主路径 |

当日额度需缓存与去重：搜索与用户数据相对宽裕；直答与问题回答很少，禁止每次心跳或每次按键调用。

## 七、时间切分（最小 MVP）

假设可投入时间为「能交一个可点开的线上 Demo」，按主路径倒排，不按模块铺开。

| 顺序 | 切片 | 完成定义 | 可砍 |
|---|---|---|---|
| P0 | 双账号登录 + 文章详情 | 两个知乎账号能登录，能打开同一篇池内文章 | 无 |
| P0 | 在场 + 邀请握手 | 一文下看见对方、邀请、同意、拒绝、超时 | 无 |
| P0 | 限时房间文字 | 进房能聊、倒计时结束不能再发 | 无 |
| P0 | 战绩条 | 结束后列表可见该局 | 无 |
| P1 | OAuth 同步创作入池 | 登录用户的文章出现在流里 | 用预置 Demo 文章 |
| P1 | 局末纪要可选保存 | 结束勾选后本人可看纪要 | 先手写/模板纪要 |
| P2 | 摸鱼流体验 | 列表下滑、在读人数 | 直接给文章 URL |
| P2 | 开局话题 | 房内展示基于摘要的讨论点 | 固定三句文案 |
| 不做 | 问题匹配队列、关注、语音、推荐、亲密度、头衔头像框、成就等级 | — | 本期内不做，养成类为战略不做 |

演示脚本固定为：两台浏览器、两个账号、一篇文章、一次邀请、一局聊天、一条战绩。任何不服务这条脚本的功能，本期不做。

## 八、明确延后的产品入口（写进规划，不写进本期开发）

完整产品有两种入口，概念上已定，实现上错开：

1. **摸鱼流 → 从内容进匹配**（本期 MVP）。
2. **带着问题 → 配同问者或答主**（下一期）。答主不在线则文章下留言，不在队列里空等。下一期复用同一套邀请、房间、战绩、纪要，只增加「问题 → 主题 → 队列」这一段。
