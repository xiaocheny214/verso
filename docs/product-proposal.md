# 背叶 / Verso Product Proposal

对外名称：**Verso**（中文 **背叶**）。本文件同步 [#30](https://github.com/xiaocheny214/verso/issues/30)，是当前唯一产品规格；旧的同文章在场邀请方案已被取代。

## 1. 产品是什么

Verso 有书面背叶之意。每个人都能借助问题，找到能力互补的人，以达到教学相长的地步。

关系模型：

```text
用户.擅长 — 对方.本次想学
用户.本次想学 — 对方.擅长

A 会写代码，想学健身
B 是教练，想搞懂互联网
→ 匹配在一起。各教一块，各学一块。各有优势，轻松社交。
```

两个条件必须同时成立：

| 这一侧 | 得到什么 |
|---|---|
| 你擅长的 | 教给还不会的人 |
| 你这次想学的 | 从对方那里学到 |

文章、关注、收藏只用来**生成擅长画像**，辅助系统找到能力互补的人。它们不是聊天地图，也不是匹配条件本身。

## 2. 用户故事

- 用知乎账号登录。系统根据用户授权的数据，标出其擅长什么。
- 用户填写一张短表单，说明这次想了解什么。表单只服务本次匹配，不写入长期画像。
- 系统找到一个能教用户想学的、同时想学用户所长的人。
- 匹配不是实时的。在 24 小时内，双方分别留下对方想学内容的答案。
- 对方敷衍时，用户先点不满意，系统再判断答案是否确实低质。确认低质才扣分；连续敷衍会临时锁住匹配资格。

## 3. 核心战略

- **只做互补。** 匹配条件是双向覆盖，不是同一话题、同一篇文章或同一个问题。
- **画像与当次需求分开。** 画像表达用户能提供什么；短表单表达用户这一次想学什么。
- **交流异步。** 双方同时在线的概率很小，互相留言比实时房间更贴合场景。
- **人先于 AI。** 只有用户先表示不满意，系统才评估内容；模型不进入对话充当第三个网友。
- **知乎提供身份与证据。** OAuth 和授权数据为画像提供来源，匹配、交换和质量流程由 Verso 完成。

## 4. 核心链路

```text
认证 → 画像 → 匹配 → 异步交流 → 质量评估
```

1. `auth`：知乎 OAuth、站内用户和授权数据。
2. `portrait`：从授权数据生成可追溯的擅长画像。
3. `match`：本次求知 Ticket 和双向互补配对。
4. `exchange`：24 小时异步互答与后续交流。
5. `quality`：对方不满意后评估本次回答。
6. `reputation`：记录评估结果和匹配资格。

模块边界以 [#31](https://github.com/xiaocheny214/verso/issues/31) 为准。

## 5. MVP 范围

### 必须完成

- 知乎 OAuth 登录，并生成有来源证据的擅长画像。
- 创建、撤销和消费一次性求知 Ticket。
- 双向互补匹配；单向覆盖和同标签互学不能误配。
- 1:1 异步互答，消息持久化，交流有明确结束状态。
- 用户先反馈不满意，系统再评估；无法判断时不处罚。

### 不做

- 同文章在场、在线读者列表、实时邀请和限时房间。
- 按同一文章、同一话题或同一个问题配人。
- 文章 Feed、地图、房间战绩和阅后即焚。
- 养成、装扮、等级、亲密度。
- AI 陪聊、每条消息实时打分、Agent 与 Agent 社交。
- 写入知乎关注、收藏、点赞或私信。

## 6. MVP 验收

统一用例：两个已登录用户，各有擅长画像，各提交一张本次求知 Ticket，系统完成双向互补配对，双方在不同时间完成互答。

1. **认证**：两个知乎账号登录后得到不同且稳定的站内身份。
2. **画像**：擅长标签带来源证据；无数据时允许明确标记的自报，不能把兴趣伪装成能力。
3. **Ticket**：同一用户同时只能有一张未结束 Ticket；匹配、撤销后状态正确结束。
4. **匹配**：双向互补能配上；只有单向覆盖、同标签互学、自己匹配自己均不能配上。
5. **异步交流**：双方无需同时在线也能留言；结束后不能继续发送。
6. **质量闸**：没有人的不满意信号就不调用评估；`good` 或无法判断不扣分。
7. **资格**：只有确认低质的结果才影响声望和后续匹配资格。

## 7. 叙事

Verso 只做一件事：**能力互补，教学相长。**

知乎内容让系统知道你能提供什么；一次性问题告诉系统你现在缺什么。Verso 找到另一张恰好能和你合上的“背叶”，让两个人各教一块、各学一块。
