# Verso / 背叶 Product Proposal

对外名称：**Verso**（中文 **背叶**）。GitHub 仓库、本地目录、Python 包一律用 `verso`（`verso_app` / `verso-common` / `verso-framework`）。
License: proprietary commercial（见仓库 `LICENSE`）。

# 项目 · 产品策划案：背叶（Verso）

立足于知乎优质内容的轻社交匹配。一篇文章当地图，开一局短对局。
本期只做可演示的一条主路径。带着问题找答主、同问者队列、跨域自动配对，都不进验收。

---

## 一、Verso 是什么

Verso 是书页背面。一页纸有两面。

关系模型一条：

```
用户 — 文章 — 用户
```

文章是桥，也是房间地图。文下看见人，发出邀请；双方同意后进限时房间；围着这篇文章聊；房毁；战绩留；纪要可选带走。仪式向游戏借（看见人、双方同意、开一局、结束）。粘性来自碰到对的人。

大模型不当第三个网友。开局话题、跑题拉回、局末纪要。用户看见房间和文章。

知乎给授权创作与搜索冷启动。邀请、房间、战绩在站内做。

### 匹配：两条策略并行

市场还没验过，**不把其中一条写成唯一正确**。两条都保留，验证后再调权重、排序、是否做成用户可选。

| 策略 | 配什么人 | 这一局图什么 |
|---|---|---|
| **同地图** | 正在读同一篇的人（读者↔读者、读者↔答主） | 共同上下文，冷场成本低 |
| **互补 / 背叶** | 能力或求知方向对偶的人 | 看起来对立，合上才是一张纸 |

互补的例子：A 会写代码、想学健身；B 是教练、想搞懂互联网。两边各缺一块，拼起来完整。身份互等：你有你的长处，我有我的长处，没有权威位。两块满足感：把你懂的教给还不会的人；学到你感兴趣的那一块。

本期 MVP **只落地同地图邀请**（一文下看见人、双方同意）。互补先写进叙事和角色（读者来学、答主来讲，也可反过来），**不单做跨域自动配对引擎**。同问者队列仍是 incoming，见第八节。

## 二、背景与战略决策

### 2.1 背景与机会

知乎上有大量垂直优质回答。日常用法多是摸鱼下滑，很少带着组织好的问题来找人。真要请教时，只能留言碰运气：对方在不在线、愿不愿意聊这一篇，都不清楚。

空白三块：

* **阅读不产生相遇**：作者信息是展示，不是可邀请的对手。
* **问答把人换掉**：直答和通用 LLM 直接给答案。
* **社交不绑内容**：没有共同地图，冷场贵，也和知乎优质内容无关。

知乎开放平台有搜索、热榜、直答、授权后的公开创作。没有「谁在线」「谁正在看同一篇」。匹配和对话必须做在第三方。黑客松要求可在线访问、接 OAuth 与开放 API：登录用 OAuth，文章池用授权创作 + 搜索兜底，直答只帮地图和纪要，不替代对话。

### 2.2 目标用户与核心问题

本期主用户是**摸鱼读者**：碎片时间下滑文章；看见文下有人，愿意开一把而不是加微信。

供给侧是**已入驻并授权的答主**：知乎上已有文章，授权后进站内池。未入驻大 V 只出冷启动名片，不能邀、不能进房。

带疑问排队、同问者匹配，都不是本期用户故事。

核心问题：以一篇知乎文章为地图，用轻量仪式（看见人 → 双方同意 → 限时房间 → 战绩 / 可选纪要），让读者和这篇文章上的人完成一次低负担相遇。同地图和互补哪条更受用，用演示和访谈看，不在规格里先判死。

### 2.3 战略决策与边界

主线：一篇文章上一局。打通看见文章 → 邀请 → 双方同意进房 → 房毁、战绩留、纪要可选。

* **决策一 · 人与人对局，不做 AI 陪聊。** 模型只做地图与纪要。
* **决策二 · 文章是地图。** 房间绑定那一篇，不先匹配再进空白聊天室。
* **决策三 · 双方同意才建房。** 邀请限时接受；拒绝或超时不建房。
* **决策四 · 房毁、战绩留、纪要自选。** 实时消息默认销毁；战绩条默认写；纪要各自勾选，存的是纪要不是逐字稿。
* **决策五 · 站内池为主，搜索为冷启动。** 可邀请的人必须已注册；（答主路径上）已授权。搜索只补未入驻名片。
* **决策六 · 匹配两条策略都留。** 同地图与互补并行。MVP 实现同地图邀请；互补先叙事、后验。未验证前不删任何一条。

核心只做匹配。养成、装扮、等级不在范围内。

### 2.4 本期范围（最小 MVP）

单地图、双人、一条主路径：

1. 知乎 OAuth 登录（昵称、头像）。
2. 授权后同步公开创作入池（标题、摘要、链接、作者）。不够则用搜索预填演示文章，标明来源。
3. 摸鱼流：文章列表；文下「当前在读 / 可邀请」（可用演示账号）。
4. 邀请握手：发起 → 限时接受 / 拒绝 / 超时；双方同意才建房。
5. 限时房间：文章地图、开局话题（模型或模板）、文字聊天、倒计时。
6. 销毁：到期或双方离开；写战绩条；问是否保存纪要。
7. 战绩列表：对局卡片；保存了纪要可点开。

incoming / 延后：带着问题找答主；同问者队列；跨域优劣势自动配对；站内关注；语音 / WebRTC；永久私信；推荐算法；知识库 RAG；多人对局。

不做：克隆知乎首页；用直答代替进房；未授权读任意知乎用户完整创作；写入知乎关注 / 点赞；完整 IM；养成装扮。

## 三、基本概念

### 3.1 文章池（Article Pool）

站内索引，不是知乎全站镜像。

| 来源 | 如何进入 | 能否作房间地图 | 作者能否被邀请进房 |
|---|---|---|---|
| 站内层 | 授权后同步的公开创作；日后站内发布（延后） | 能 | 能（作者已入驻） |
| 冷启动层 | 搜索缓存的标题、摘要、链接、作者展示 | 能（演示阅读） | 不能，只出名片 |

MVP 匹配对象是站内层。冷启动用来撑浏览，并讲清「入驻前只能看不能邀」。

### 3.2 用户角色（一局里的位置）

同一登录用户，不同局可以是不同位置：

* **读者**：摸鱼流进来、打开这篇文章。
* **答主**：这篇文章的作者，且已入驻。
* **同主题读者**：也在读这篇、不是作者。文下在场，不是同问者排队。

MVP 不单独做答主排队、同问者队列。可邀请的人 = 此刻这篇文章上的在线用户（含在线作者）。列表可标明角色（答主 / 同读），方便用户自己选同地图还是互补，系统不替用户判死。

### 3.3 在场（Presence）

打开某篇文章即上报在场。离开页面或心跳超时离场。邀请列表只来自在场。MVP 用 WebSocket 或短轮询。

### 3.4 邀请（Invite）

限时握手：发起者、被邀请者、文章 ID、倒计时。

状态：已发出 → 已接受 / 已拒绝 / 已超时 / 已取消。

只有「已接受」才建房。邀请不是房间。

### 3.5 房间（Room）

字段：房间 ID、文章 ID、双方、开始 / 结束时间、状态。

* 双方同意之后才创建。
* 固定时长（建议 10–15 分钟），可提前离开。
* 房内文字经 WebSocket 转发，默认不永久存。
* 到期或双方离开后关信道、丢实时消息。

### 3.6 地图与局内模型（Map）

地图 = 绑定的文章（标题、摘要、原文链接、作者）。

模型只做三件事，且必须 grounded 在这篇文章：

1. 开局 1–3 个可讨论点。
2. 跑题时拉回原文（MVP：手动「拉回地图」+ 一次生成）。
3. 局末短纪要。

用户不与模型对聊。额度紧时开局用摘要截句模板，纪要再生成一次。

### 3.7 战绩（Match Record）

结束后默认一条短记录，不含聊天原文。

字段：时间、文章标题与链接、对方展示名、本局角色（读者 / 答主 / 同读）、是否成局、时长、是否保存纪要。

用来回想碰过谁、从哪篇开的局。

### 3.8 纪要（Summary）

局末按地图 + 对话生成若干条。销毁前每人独立选 **保存 / 不保存**。保存的是纪要，挂在自己的战绩下。默认不保存。

### 3.9 主题（Topic）

标题、摘要收到主题键。MVP 用同一 `article_id` 做同地图匹配，不上 embedding。按用户问题做主题归一、按优劣势做跨域互补，都留给后续。

## 四、核心流程与原型

主界面摸鱼流。资产：文章池 + 战绩。

1. 知乎 OAuth 登录，展示昵称与头像（知乎 / 人工）。
2. 同步公开创作入池；不足则搜索预填并标来源（知乎 / 工程）。
3. 打开一篇文章，进入在场（人工 / 工程）。
4. 文下看到其他人，发出邀请；对方倒计时接受或拒绝（人工 / 工程）。
5. 双方同意 → 建房，加载地图与开局话题（工程 / 模型）。
6. 限时文字；倒计时可见（人工 / 工程）。
7. 关房，丢实时消息；写战绩；问是否保存纪要（工程 / 模型 / 人工）。
8. 战绩里看到这局；保存了纪要可回顾（人工）。

Demo：两台浏览器、两个账号、一篇文章、一次邀请、一局聊天、一条战绩。不要求大规模在线。

## 五、核心假设与验收

### 5.1 核心假设

| # | 核心假设 | 验证方式 | 通过标准 | 失败退路 |
| - | --- | --- | --- | --- |
| 1 | 用户要在优质文章上碰到人，要房间，不要更好的推荐流或纯 AI 答案 | 演示后访谈：能否复述地图 / 邀请 / 销毁 | 多数人能独立复述这三件 | 收成文下在线 + 留言 |
| 2 | 双方同意比自动进房更可接受 | 对比打扰评价 | 多数人认为确认后进房可接受 | 仅答主可被邀请 |
| 3 | 文章当地图能降低冷场 | 有地图开局 vs 空白房，看前 1 分钟开口 | 有地图时开口更好或更贴原文 | 固定问题模板 |
| 4 | 房毁 + 战绩 + 可选纪要够回顾 | 结束后能否找回对手与文章 | 能在战绩里找到 | 加 24h 回放，仍不永久 IM |
| 5 | 授权公开创作够撑 Demo 池 | 2 个授权账号能否列出可点开的文章 | 至少 1 篇能做地图 | 搜索预填，UI 标冷启动 |
| 6 | OAuth + 搜索 / 直答能说清「立足于知乎」而不越权 | 评审能指出：登录和文章来自知乎，匹配和房间是 Verso | 边界说得清 | 界面加来源标记 |
| 7 | 同地图与互补哪条更受用，尚未知道 | 访谈与对局后问：更想找同读，还是找能补另一面的人 | 先收集偏好，不据此砍功能 | 只调列表排序或文案，两条策略都留 |

### 5.2 验收标准

统一用例：两位登录用户，在同一篇已入池文章下完成一次对局。

现状：知乎读完无法确认作者或其他读者是否在线、是否愿意聊这一篇。

通过 / 不通过：

1. **登录**：知乎 OAuth，展示昵称、头像。
2. **文章可开局**：池中至少一篇有标题、摘要、原文链接、作者，可作地图。
3. **在场可见**：打开该文后，另一在场用户出现在可邀请列表。
4. **握手**：被邀请方看到倒计时；拒绝或超时不产生房间；同意才进房。
5. **房间绑地图**：房内固定展示该文；可发文字；有倒计时。
6. **销毁**：结束后不能再在该房发消息；对话不进永久私信。
7. **战绩**：双方列表出现该局卡片（文章、对手、时长）。
8. **纪要可选**：每人可保存或不保存；保存后仅本人能在该条战绩下看到。

边界：未登录不能邀请；对象已离场则失败并提示；未双方同意不建房；冷启动未入驻作者不能邀；没有地图文章不建房。本期不验收跨域自动配对。

## 六、与知乎开放能力的对照

| 产品能力 | 用哪类知乎能力 | MVP 是否必须 |
|---|---|---|
| 登录与名片 | 黑客松 OAuth | 必须 |
| 站内文章池 | `user/contents`（授权用户公开创作） | 必须（可加搜索兜底） |
| 冷启动名片 | `zhihu_search` | 可选兜底 |
| 开局话题 / 纪要 | 直答或自有 LLM；额度紧时模板 + 一次生成 | 纪要建议有，开局可模板 |
| 在场、邀请、房间、战绩 | 无对应知乎 API，全部自建 | 必须 |
| 关注、收藏作兴趣向量 | `followees` / `favorites` | 延后（互补策略以后可能用） |
| 问题下全部回答列表 | `question_answers`（无作者、额度低） | 不做主路径 |

搜索与用户数据相对宽裕；直答与问题回答很少。禁止每次心跳或每次按键调用。

## 七、时间切分（最小 MVP）

按主路径倒排。

| 顺序 | 切片 | 完成定义 | 可砍 |
|---|---|---|---|
| P0 | 双账号登录 + 文章详情 | 两个知乎账号能登录，能打开同一篇池内文章 | 无 |
| P0 | 在场 + 邀请握手 | 一文下看见对方、邀请、同意、拒绝、超时 | 无 |
| P0 | 限时房间文字 | 进房能聊、倒计时结束不能再发 | 无 |
| P0 | 战绩条 | 结束后列表可见该局 | 无 |
| P1 | OAuth 同步创作入池 | 登录用户的文章出现在流里 | 用预置 Demo 文章 |
| P1 | 局末纪要可选保存 | 结束勾选后本人可看纪要 | 先手写 / 模板纪要 |
| P2 | 摸鱼流体验 | 列表下滑、在读人数 | 直接给文章 URL |
| P2 | 开局话题 | 房内展示基于摘要的讨论点 | 固定三句文案 |
| incoming | 带问题找答主、同问者队列、跨域自动配对、关注、语音、推荐 | — | 本期内不做 |

演示脚本：两台浏览器、两个账号、一篇文章、一次邀请、一局聊天、一条战绩。不服务这条脚本的功能，本期不做。

## 八、incoming 能力

本期入口只有一条：**摸鱼流 → 从内容进匹配**。

后续第二种入口，优先 **带着问题 → 配垂直领域答主**（一人可对多个领域答主）。复用邀请、房间、战绩、纪要。答主不在线则文章下留言，不在队列里空等。这条和「互补」相关，但仍是后续，不进本期验收。

**同问者匹配**标为 incoming：仅按同一问题配人，难确认是否真同问、该配什么视角，与一文下邀请重叠，收益低。日后要做须单独开提案。

**跨域优劣势自动配对**（健身×开发那种）也是 incoming：要先有可靠的长短板信号。在那之前，互补只存在于叙事、角色展示和用户自己选人。
